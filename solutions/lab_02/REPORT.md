### Задание 1 Имена и изменяемость

Файл: `task_1.py`.

Прогноз A: после `b = a` имена связаны с одним целым числом. После `a += 1` получатся значения 11 и 10, идентификаторы станут различаться.

Фактически: сначала выведены 10 и 10 с одинаковыми `id()`, затем 11 и 10 с разными `id()`. Целое число неизменяемо: операция не изменяет объект 10, а связывает имя `a` с результатом 11. Имя `b` продолжает обозначать 10.

Прогноз B: `second.append(30)` изменит общий список. Новый список с теми же значениями будет равен исходному по `==`, но отличаться по `is`.

Фактически: оба имени сначала показывают `[10, 20]`, после `append` — `[10, 20, 30]`; их идентификаторы равны. После `second = [10, 20, 30]` результат `==` равен `True`, а `is` — `False`. Добавление 40 изменяет только `second`: `first` остаётся `[10, 20, 30]`.

Схемы связей до и после переназначения приведены ниже.

```text
До:     first  -> список A [10, 20, 30] <- second

После:  first  -> список A [10, 20, 30]
        second -> список B [10, 20, 30]
```

Рисунок 1 — Связи имён и списков до и после переназначения

Практическая задача. Конфигурация содержит имя проекта, `members` и вложенный список `parameters`. Прогноз: простое присваивание оставит общий словарь, глубокая копия даст независимые изменяемые объекты.

Фактически: добавление Анны и замена `debug` на `release` через `alias` видны в `project`. После `deepcopy()` добавление Ивана и установка четырёх исполнителей меняют только независимую конфигурацию. В исходной остаются Лев и Анна, число исполнителей равно 1. Проверки `assert` подтверждают различие словарей, списков участников, списков параметров и каждой вложенной строки.

Ответы на вопросы. 1. Присваивание `second = first` не меняет объект; оно создаёт связь имени с уже существующим объектом. 2. Неизменяемый объект нельзя изменить на месте, поэтому имя связывается с результатом операции. 3. Проверка `is` определяет идентичность; одинаковый `id()` у одновременно существующих объектов также означает один объект. Проверка `==` сравнивает значения.

### Задание 2 Копирование

Файл: `task_2.py`.

Прогноз: добавление предмета во внешний список затронет `original` и `alias`. Изменение вложенной оценки затронет также `shallow`. Копия `deep` сохранит исходные данные.

Фактически: после добавления Databases длины `original` и `alias` равны 3, остальных — 2. После изменения оценки Python исходный список, псевдоним и поверхностная копия содержат оценку 3, глубокая копия — 5. Идентификаторы внешних списков у `original` и `alias` совпадают; у остальных различаются. Первая вложенная строка общая у `original`, `alias`, `shallow`, но отдельная у `deep`.

До изменения оценки объект числа 5 общий даже у глубокой копии: неизменяемые целые числа не требуется дублировать. После изменения в исходной строке сохранена ссылка на 3, а в глубокой копии — на 5. Полные идентификаторы выведены в протоколе запуска.

Сравнение способов копирования представлено в таблице 1.

Таблица 1 — Способы копирования исследованного списка

| Операция | Новый внешний объект | Новые вложенные объекты | Изменения независимы |
|---|---|---|---|
| Присваивание | Нет | Нет | Нет |
| Поверхностная копия | Да | Нет | Только изменения внешнего списка |
| Глубокая копия | Да | Да, вложенные списки | Да, в исследованной структуре |

Матрицы. Прогноз: `[[0] * 3] * 3` повторит ссылку на одну строку; списковое включение создаст три строки. Фактически после изменения `[0][0]` ошибочная матрица равна `[[1, 0, 0], [1, 0, 0], [1, 0, 0]]`, правильная — `[[1, 0, 0], [0, 0, 0], [0, 0, 0]]`. В первом случае три идентификатора строк одинаковы, во втором все различаются. Это проверено без `deepcopy()`.

Ответы на вопросы. 1. Поверхностная копия создаёт внешний контейнер и сохраняет ссылки на его элементы; глубокая рекурсивно копирует вложенные изменяемые объекты [1]. 2. Глубокое копирование требует времени и памяти, может дублировать данные, которые должны быть общими, и подходит не для всех ресурсов [1]. 3. Поверхностной копии достаточно для независимого добавления или удаления элементов внешнего списка, если вложенные объекты не меняются либо неизменяемы.

### Задание 3 Подсчёт ссылок и слабые ссылки

Файл: `task_3.py`.

Прогноз: создание псевдонима и помещение списка в контейнер добавят по одной сильной ссылке. Удаление псевдонима и очистка контейнера уберут по одной ссылке.

Фактически в CPython 3.11.9 последовательность счётчиков: `2 -> 3 -> 4 -> 3 -> 2`. При прямом вызове `sys.getrefcount(data)` здесь учитывается временная ссылка аргумента [2]. Абсолютное число не является постоянным свойством списка: в проверенном CPython 3.14.7 получено `1 -> 2 -> 3 -> 2 -> 1`, но изменения остаются теми же. Проверки в коде используют разницы относительно начала.

Прогноз для `weakref.ref`: после удаления единственной сильной ссылки вызов слабой ссылки вернёт `None`. Фактически сначала выведен объект `Record`, после `del record` — `None`.

Практическая задача. Прогноз: слабый реестр сначала содержит три записи, после удаления `temporary` — две, после удаления `second` — одну. Фактически состав изменился так: `['first', 'second', 'third'] -> ['first', 'second'] -> ['first']`. Проверки `assert` пройдены. Слабые ссылки полезны, например, в кеше изображений: кеш позволяет найти объект, пока он нужен программе, и не удерживает его после удаления остальных ссылок [3].

Ответы на вопросы. 1. Для обычного объекта в исследуемой сборке CPython достижение нулевого числа сильных ссылок позволяет освободить объект. `del alias` удаляет связь имени, а не требует немедленно уничтожить объект. 2. Освобождение объекта не обязательно возвращает память операционной системе: интерпретатор может оставить блоки для повторного использования. 3. Сильная ссылка удерживает объект, слабая не продлевает его жизнь; после уничтожения объекта `weakref.ref()` возвращает `None` [3].

### Задание 4 Циклы и сборщик мусора

Файл: `task_4.py`.

Прогноз: два списка, ссылающиеся друг на друга, после удаления внешних имён останутся с внутренними ссылками. Ручная сборка обнаружит недостижимый цикл.

Фактически обе проверки взаимных ссылок дали `True`. Перед удалением сохранены числовые `id()`, которые сами не удерживают списки. После `del first, second` вызов `gc.collect()` вернул 2. В начале запуска автоматическая сборка была включена; пороги CPython 3.11.9 равны `(700, 10, 10)`. Статистика поколений выведена в протоколе. Возвращаемое число относится ко всей сборке и в другом запуске может включать дополнительные недостижимые объекты [4].

Прогноз дополнительного опыта: при отключённой автоматической сборке пять списков со ссылкой на себя останутся до ручной сборки. Фактически `gc.isenabled()` вернул `False`, ручной вызов собрал 5 объектов. В блоке `finally` выполнен `gc.enable()`, после него состояние — `True`.

Практическая задача. Созданы три словаря с полем `links`, образующие цикл, и независимый словарь D. Схема графа показана на рисунке 2.

```text
A -> links_A -> B -> links_B -> C -> links_C -> A
D -> links_D -> []
```

Рисунок 2 — Цикл трёх узлов и независимый узел

Прогноз: после удаления `a`, `b`, `c` недостижимыми станут три словаря и три списка связей; D сохранится. Фактически сборка до создания графа вернула 0, после удаления внешних имён — 6. Переменная `independent` по-прежнему содержит `{'name': 'D', 'links': []}`; это подтверждено `assert`. На время этого опыта автоматическая сборка также отключена и восстановлена в `finally`.

Ответы на вопросы. 1. Цикл возникает при прямой или косвенной ссылке объекта на себя. 2. Внутренние ссылки в цикле поддерживают ненулевые счётчики, даже когда из программы к объектам уже нет пути. Поэтому одного подсчёта ссылок недостаточно. 3. Поколения позволяют чаще проверять молодые объекты и реже долго живущие, уменьшая затраты на сборку. Конкретная организация поколений и пороги зависят от версии CPython [4]. Постоянные ручные вызовы сборки в обычной программе не требуются.

### Задание 5 Исследование памяти

Файлы: `task_5.py`, `memory_report.py`. Первый файл вызывает итоговую утилиту. Функция `collect_measurements()` сначала сохраняет результаты в списке словарей и списке пар, `print_report()` затем оформляет вывод.

Прогноз для размеров: внешний размер списка не включает полную память всех целых чисел; кортеж с теми же десятью значениями будет компактнее списка. Фактические размеры приведены в таблице 2.

Таблица 2 — Размеры внешних объектов в CPython 3.11.9

| Объект | Размер, байт |
|---|---:|
| Пустой список | 56 |
| Список 10 целых чисел | 136 |
| Кортеж тех же чисел | 120 |
| Строка из 10 символов a | 59 |
| Целое число 42 | 28 |
| None | 16 |

`sys.getsizeof()` измеряет собственную память объекта [2]. У списка это в том числе память под ссылки, но не полная память объектов-элементов. Нельзя бездумно суммировать размеры вложенных объектов: один объект может встречаться несколько раз.

Прогноз роста: размер будет увеличиваться скачками, а не после каждого `append()`. Фактически за 100 добавлений зафиксированы пары «длина — байты»: `0 — 56; 1 — 88; 5 — 120; 9 — 184; 17 — 248; 25 — 312; 33 — 376; 41 — 472; 53 — 568; 65 — 664; 77 — 792; 93 — 920`.

Список резервирует место с запасом, чтобы не перевыделять массив ссылок при каждом добавлении. Длина — количество текущих элементов; выделенная память включает служебные данные и резерв под будущие элементы. Например, размер не меняется при росте длины от 1 до 4.

Прогноз `tracemalloc`: материализованный список из 100 000 чисел потребует значительно больше памяти, чем `range`. Для каждого сценария трассировка запускается заново и останавливается в `finally`. Значения current и peak считываются, пока объект ещё существует; форматирование выполняется после измерений. Результаты представлены в таблице 3.

Таблица 3 — Сравнение представлений 100 000 чисел

| Сценарий | Число элементов | Внешний размер, байт | Текущая память, КиБ | Пиковая память, КиБ |
|---|---:|---:|---:|---:|
| list(range(100000)) | 100000 | 800056 | 3898.2734 | 3898.3828 |
| range(100000) | 100000 | 48 | 0.0781 | 0.1250 |

КиБ = 1024 байта. Отношение пиков: `3898.3828 / 0.1250 ≈ 31187.06`. Это результат данного запуска, а не универсальная константа. Список хранит ссылки на материализованные значения; `range` хранит параметры последовательности и вычисляет значения по запросу.

Утилита дополнительно выводит число элементов, внешний размер, current и peak для всех шести малых объектов из таблицы 2. Число элементов для 42 и None условно принято равным 1. Полная таблица есть в `EXPERIMENTS.txt`. Некоторые текущие значения равны нулю: `tracemalloc` учитывает отслеженные выделения после `start()`, а не полную память процесса; константы уже существовали до начала трассировки, возможна повторная выдача ранее выделенных блоков [5]. В CPython 3.14.7 измеренный пик `range` также оказался нулевым. Утилита сообщает, что отношение в этом случае не определено, и не делит на ноль. Сам объект всё равно имеет ненулевой внешний размер.

Итоговый анализ. 1. Для последовательного перебора чисел использовать `range` вместо `list(range(...))`, когда список не нужен: это подтверждено измерением 100 000 элементов. 2. Не применять глубокое копирование автоматически: для изменения только внешнего списка достаточно поверхностной копии, как показало задание 2. 3. Удалять ненужные сильные ссылки и применять слабые кеши, если они не должны владеть объектами: опыт с реестром показал автоматическое исчезновение записей. 4. Для неизменяемого набора значений рассматривать кортеж: в данном опыте внешний размер 120 байт против 136 у списка. Выбор всегда должен сохранять нужное поведение программы.
